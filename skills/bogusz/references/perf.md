# Mode H: performance

- **Code level:** use the stack's benchmark tool on the base and on the change, with repeats. Build the base in a separate worktree (`git worktree add <tmp dir> <base>`, removed afterwards); never stash, switch branches or check out files in the user's tree. For Go: `go test -bench=<Name> -benchmem -run='^$' -count=6 ./<pkg>/...`, compared with `benchstat` if it is installed; its median ± CI and p-value decide significance for these rows. For Python: `pytest-benchmark` or `pyperf` if the project uses them. For JS: the project's own bench script. Report per-op time and allocations with the deltas.
- **Before any harness or load run:**
  - Run it only against a target the profile's `## Environments` marks safe, a local one, or one the user named in this request.
  - Read the harness before running it. If it builds, deploys or changes anything a `## Forbidden commands` entry covers, it needs the user asking in this request.
  - State the virtual users, duration, target and where the load comes from (this machine, inside the cluster, CI) first. When the load crosses a proxy, ingress or WAN the production callers don't, say the latency includes that hop. Load on a shared environment needs an explicit yes, because it affects other people.
- **Harness first:** if the profile names a `Bench harness`, run it and report on its output; don't write a k6 script beside it. The harness owns the project-specific parts (where the load runs, image builds, cluster setup). Read its per-run output files, not only its console summary.
- **Load:** with no harness, use the load script from the profile (for example a k6 or Locust file) if there is one; otherwise propose a minimal k6 script and show it before running. Report p50/p95/p99 latency, the error rate, the throughput and the thresholds.
- **Matrix:** when the run varies parameters (replicas, workers, payload size, implementation), each combination is one point. Every rule below applies per point.
- **Repeats:** at least 3 runs per point for load and harness runs. Repeats done inside the harness count only when its output gives each run separately; an averaged number is one run. Report the median and the min–max range. Call a difference a regression or an improvement only when the base and change ranges don't overlap; otherwise report it as within noise, with the spread in %. The base range comes from running the base with the same repeats (deploy or build the base the same way, or check it out in a separate worktree); a baseline with one number per point cannot back the call. Never call a single run a regression or an improvement.
- **Parity before speed:** when the run compares two implementations or variants of the same thing, first check that they return the same results on the same inputs, exactly or within a tolerance you state. A mismatch fails the comparison, however fast the faster one is.
- **Server-side metrics:** if the profile names `Resource metrics` (a sidecar, `kubectl top`, the app's own timing or stage log), sample it throughout the run, not once before or after, and report the peak and mean CPU and memory of the system under test and the per-stage time next to the latency. Otherwise list them under `## Known limitations`.
- **Baselines:** compare with the profile's `Baseline` (a results file in the repo) when there is one, otherwise with the previous `*-perf-<slug>.md` report in `~/.bogusz/reports/`. Propose new results for the baseline file as a dated column holding the median and min–max; edit it only when the user asks.
