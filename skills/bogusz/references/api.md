# Mode J: API and client

For any project that serves an API (HTTP/REST, GraphQL, gRPC, WebSocket) or ships a client library or SDK that calls one, in Python or any other language. Nothing here is tied to one product: the profile and the code name the spec, the server and the client.

1. **Find the contract.** Start from the profile's `## UI, performance and security entry points`. Otherwise look for an OpenAPI or Swagger file (`openapi*.yaml`, `openapi*.json`, `swagger*`), `*.proto`, a GraphQL schema (`*.graphql`), the route or handler table, and the client's public surface (for Python: what the package exports in `__init__.py` or `__all__`, its public classes and methods, its type stubs). Write the expected behaviour from the spec and the docs, not from the implementation. Where the spec and the code disagree, that is a finding.
2. **Plan each operation in scope** (Mode B table, layer `unit`, `integration`, `API` or `E2E`, as step 3 maps them). Pick the cases that apply:
   - **Happy path:** the status or return value, and a response shape that matches the spec.
   - **Validation:** a missing required field, a wrong type, empty, oversized, an unknown field → the documented 4xx or client exception, never a 500 or a crash.
   - **Auth:** no credentials, a bad or expired token, another tenant's resource → the documented 401, 403 or 404. Test cross-tenant access with two test accounts you own; with only one, mark the case `[not run]` and say why. Deeper authorization work is Mode I.
   - **Errors:** not found, conflict, server error. How the client maps HTTP or gRPC errors to its exceptions, and whether it keeps the status and message.
   - **Paging, filtering, sorting:** first and last page, an empty result, the page-size limit, a client iterator that stops.
   - **Retries and timeouts:** a repeated PUT or DELETE is idempotent; the client retries 429 and 503, honours `Retry-After`, gives up after its limit, and never retries a non-idempotent call silently.
   - **Serialization:** dates and time zones, decimals, Unicode, null vs missing, enums, and unknown fields from a newer server (the client must not break on them).
   - **Client configuration:** base URL, the auth header actually sent, the user agent, and no secret in `repr`, logs or exception text.
   - **Compatibility:** a removed field, a new required field or a renamed operation breaks the consumers in `## Cross-repo / API consumers`; test the client against each server version the project supports.
3. **Choose the layer.** Use the narrowest one that proves the case:
   - **Client unit** (`unit`): stub only the network, with the HTTP mocking the project already uses: Python `httpx.MockTransport`, `respx`, `responses`, `requests-mock`, `pytest-httpserver`, `aioresponses`; Go `httptest.Server`; JS `msw`, `nock`. Assert the request the client sent (method, path, query, headers, body) and what it did with the response. Take canned responses from the spec or the docs' examples, never from the client's own models.
   - **Server handler** (`API`): the framework's in-process test client, such as FastAPI or Starlette `TestClient`, Flask `test_client()`, Django `Client`, Go `httptest.NewRecorder`, `supertest`.
   - **Integration** (`integration`): the real client against a local server started from the profile (in the background; stop it when done). This proves both sides agree.
   - **Contract** (`API`): the spec tools the project already runs, such as `schemathesis run <spec> --url <local base URL>`, Pact, `buf breaking`, `oasdiff`. Adding a tool the project doesn't use needs a stated reason and a yes.
   - **Ad-hoc probe** (`API`): `curl -sS -i`, `grpcurl`, or a short script that uses the project's client, to reproduce one call. Keep the exact command, the status and the fields the case is about as evidence. Leave out every token, cookie, session id or other credential the response carries: the redaction script knows only common credential shapes, so an opaque session value gets past it. If the case matters, turn it into a test.
4. **Run it in the project's environment.** Use the profile's command or the project's runner (`uv run pytest`, `poetry run pytest`, `tox -e <env>`, `npm test`). If the client has no environment yet, create a throwaway virtualenv outside the repo and install the client with its test dependencies: `python3 -m venv <tmp dir>`, then `<tmp dir>/bin/pip install -e '<client repo>[<test extra>]'`, where `<test extra>` is the test group in its `pyproject.toml` (with none, also install the runner and the test libraries by name). An editable install can leave `*.egg-info` or `build/` in the repo: remove what `git status` shows the install added, and nothing else. Never install into the system Python or the user's active environment.
5. **Target and data.** A local server, an environment the profile's `## Environments` marks safe, or one the user named in this request (Mode C rules). Anywhere but local, send read-only calls (GET, queries, list RPCs) by default. A mutating call (POST, PUT, PATCH, DELETE, a mutation, a writing RPC) needs a yes, uses only test data you create, and cleans it up afterwards. Never touch other users' data. Before the first mutating call, even to a local server, check where that server stores data (its `DATABASE_URL` or equivalent setting): a local process that writes to a shared database counts as that shared environment. Keep the request rate low; load belongs to Mode H.
6. **Credentials** come only from the environment variables the profile names. Reference them unexpanded (`-H "Authorization: Bearer $API_TOKEN"`), so the command you run and report holds no secret. Never print a token or a response field that holds one.
7. **Report it.** Use the API section of the test report. The session record (`sessions.py tests`) lists test runners only, so `curl`, `grpcurl` and contract tools such as `schemathesis` are not in it: quote each such command and the lines of output you relied on yourself, tagged `[ran: <command>]`. A failure that is a product bug goes through Mode F, with the `curl`, `grpcurl` or client call as the minimal repro.
